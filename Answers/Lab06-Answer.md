# Lab 6 参考答案

[题目](../Labs/Lab06-Physical-Design/Lab06.md) · [答案目录](README.md)

## 一份可以复现的数据准备

在新的性能练习库里执行 schema、seed、[benchmark.sql](SQL/benchmark.sql)。预期额外生成200名学生、50场活动、10000份已取消历史和2000份当前报名；每个新增学生有50份历史与10份当前报名。当前报名分布在10场新活动中，每场200人、容量300，没有超额或重复当前报名。

学生与活动的组合由整数商和余数分配，不是所有记录都挤到一个学生。它仍是人工均匀数据，与真实开学高峰不同，因此结论只适用于此负载。benchmark只运行一次，重复执行会遇到合成编号冲突。

## 两个索引为什么这样排

学生历史查询的条件是 student_no 相等，然后按 requested_at、attempt_id 排序，所以候选为 (student_no,requested_at,attempt_id)。原来的唯一索引以学生和活动开头，可能已能定位这个学生，但未必能顺着所需时间顺序读取。

活动当前名单的条件是 event_id 与 state 相等，再按时间和尝试号排序，所以候选为 (event_id,state,requested_at,attempt_id)。状态单独选择性可能不高，不表示它永远不能参与联合索引；要看前面的活动条件与实际数据。

写法见 [indexes.sql](SQL/indexes.sql)。不是要求两个都保留：比较计划、空间与写入代价后，可以删掉不划算的额外索引。别删除主键、业务唯一约束或外键依赖的保护。

## 计划里应该读什么

先比较访问路径，再看有无额外排序、返回量和循环次数。EXPLAIN 的估计行数不是实测扫描量；EXPLAIN ANALYZE 会执行 SELECT，给迭代器实际统计，循环节点的含义要结合 loops 理解。[EXPLAIN 文档](https://dev.mysql.com/doc/refman/8.0/en/explain.html)

合理假设是索引可能减少排序、减少候选行；但小数据或高返回比例时，优化器可能选择别的路径。**这里没有给“快了多少倍”的标准数值，也没有实测截图。**学生应保存自己的原始计划与至少三次预热后测量，使用中位数并注明波动。

查询必须保持同样的列、过滤和排序。把 SELECT * 改成只查两个列再说“全是索引的功劳”，会混入另一个变量。覆盖查询可以另外作第二组实验。

## 回表、B+ 树与 Hash

InnoDB 有明确主键时，以主键形成聚簇索引，叶子保存行；二级索引记录中带有对应主键。二级索引定位后，如果还需不在索引里的信息，通常需要回到聚簇索引取行。覆盖查询的所需信息在索引中已具备，可减少这类访问。[聚簇与二级索引](https://dev.mysql.com/doc/refman/8.0/en/innodb-index-types.html)

有序树结构支持等值、范围与有序扫描；Hash 的常见强项是等值定位，本身不提供同样的范围顺序。InnoDB 自适应 Hash 是内部机制，不能当作普通表上任意 CREATE INDEX USING HASH 的承诺。[自适应 Hash](https://dev.mysql.com/doc/refman/8.0/en/innodb-adaptive-hash.html)

## 对应任务五：检查结构与解释代价

执行indexes.sql末尾的SHOW INDEX，核对两个候选索引分别从学生/活动过滤条件开始，后接所需时间顺序。主键和原有唯一约束索引仍然存在，不能把它们当成无用重复全部删除。

新增报名时，除原有结构外还要维护这两个新索引；修改state会影响活动状态索引，修改requested_at会影响两个时间索引。它们增加结构空间和写维护工作，是否值得取决于读写负载与查询改善。本项要求观察结构并解释成本，不要求拿到规定的性能提升或写入时间。

## 选做：写入成本怎么公平比较

准备两份相同的性能库，一份只有必要索引、一份有额外查询索引；对同一批新历史记录做相同事务批量写入。写入行数、约束、提交次数、硬件和连接条件保持一致。比较多次耗时与索引空间，不能靠一次波动下结论。

增加索引需要维护更多结构，通常增加空间与写维护工作；某次耗时恰好更低不推翻这个机制，也不代表所有负载都该少建索引。事务回滚也会做工作，所以不要用“插入再回滚”的整段时间当成纯提交写入时间。

重复读取可能受 Buffer Pool、操作系统缓存等影响；InnoDB 缓存数据页和索引页。冷热现象值得观察，但别把一次变快全归因于一种缓存，更不要为了实验清理共享服务器缓存。
