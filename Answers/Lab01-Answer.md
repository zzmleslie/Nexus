# Lab 1 参考答案

[题目](../Labs/Lab01-Requirements/Lab01.md) · [答案目录](README.md)

本页四部分依次对应新版讲义的四项任务。先以[业务背景与需求](../00-业务背景与需求.md)为依据，再比较本答案采用的暂定方案。

## 1. 谁做什么

学生提交入社申请、查看结果：需要知道申请哪个社群、何时提交、是否处理。学生报名或取消活动：需要看到举办时间、报名窗口、当前结果和自己过去的尝试。

负责人处理本社群申请：需要看到申请人、申请时刻和当前是否待审。负责人发布活动、查名单：需要填写时间、容量，看到当前正式名单与剩余名额。

管理员维护社群资料、指定负责人：需要区分社群和被指定的人。管理员查异常：例如同一活动当前人数超限、同一人有重复有效资格。异常查询是补充的运营需求，不等于可以绕过业务规则。

学生姓名可以重复；负责人可以同时也是学生。能在业务上管理一个社群，不代表这个人天然拥有数据库账号或全库权限。

## 2. 覆盖上述操作的数据字典

下面按业务信息分组。每条说明含义、取值与缺失条件、来源和用途；分组不代表怎样分表。标识用于分辨业务实例，具体生成方式留给后续设计。

- **学生身份与展示资料**：学号是学校分配的不重复、不回收文字编号，必填；姓名必填但可重复，院系在本参考版允许未知。学校资料提供，学生申请、报名和负责人核对名单使用；学号不能转数值后丢掉前导零。
- **社群标识与名称**：标识必须能区分不同社群，名称是必填展示文字、不保证唯一。管理员登记或维护，学生选择社群及负责人确认操作范围使用。
- **社群介绍**：说明社群方向的文字，本版本允许尚未补充；管理员维护，供学生浏览，不用它识别社群。
- **当前负责人**：管理员指定的学生身份，必须能对应已登记学生。本版本允许初建社群暂缺负责人，但有负责人后才允许正常发布；用于管理范围判断，不用于推断过去授权。
- **申请标识、申请人和目标社群**：每次独立申请都必须能分辨，并明确属于谁、申请哪里。申请人选择目标、受理过程确认身份与本次经历，用于审批和结果查询；不得把同人同社群的全部历史当成一次。
- **申请时刻**：本次提交被受理的时刻，必填，由受理过程记录，用于顺序、等待时间及历史查询，不能由重新申请覆盖旧值。
- **申请处理及成员结果**：本版本区分待审、拒绝、撤回、当前有效、已退出；受理或相应业务操作产生。待审没有处理时刻，处理后必须有处理时刻且不早于申请；拒绝理由必填，其他说明可空。学生看结果、负责人找待办和核对资格时使用。
- **加入与退出时刻**：获批才有加入时刻，未获批时不适用；获批时由审批过程记录，当前有效者尚无退出时刻，退出后必须保留且晚于加入。用于解释[加入,退出)及多次经历，不仅凭“退出为空”判断成员身份。
- **活动标识、标题和主办**：每场活动必须可区分，标题必填但可重复，恰有一个已登记主办社群。负责人发布时提供/确认，用于浏览、报名、名单与分组统计。
- **活动举办起止**：必填时刻，开始早于结束；负责人设置，供学生安排与查询时间范围使用，不等同报名窗口。
- **报名开放与截止**：必填时刻，开放 < 截止 ≤ 活动开始；负责人设置，报名与自助取消均按[开放,截止)判断。
- **活动容量与业务状态**：容量是必填正整数，不能用零代表未知；本参考版状态区分已发布、已取消。负责人发布或有权管理操作提供，学生判断可报名、负责人核对当前人数使用。
- **报名尝试标识、学生和活动**：一次受理必须能分辨，且必须属于已登记学生与活动，由受理过程确认。历史查询可区分取消后重报，当前名单不能重复计同一学生。
- **受理时刻与当前报名结果**：受理时刻必填，本版本结果为当前正式或已取消；分别由受理和取消过程产生，供名单、名额及历史查询使用，未成功受理不伪装为正式报名。
- **取消时刻与原因**：当前正式者没有取消时刻，取消后必须有且不早于受理；取消过程记录。原因在最小版允许空，若有则用于解释学生取消或活动取消，不清空原受理时刻。
- **当前正式人数与剩余名额**：派生整数，由当前正式报名事实计算；无人时为0，剩余=容量−人数，不存在“因未计算而当成零”的含义。负责人查看名单、管理员查超额异常及学生浏览名额时使用，不混计取消历史。

入社数据流可以写成：学生提交申请材料 → 负责人检查是否重复及是否有权处理 → 写下结果 → 学生查询结果。数据结构例子是“一份申请材料”；数据存储例子是“需要保留的历次申请与成员经历”；处理过程是“审批申请”。这些需求视角不直接规定表数量。

## 3. 规则与没说清的地方

三组正反例：两个学号不同但同名的学生允许存在，重复学号拒绝；容量1且无人正式报名时可受理首人，已有一人后不能再正式受理第二人；窗口[10:00,12:00)内11:00可受理，12:00整拒绝。

参考版本的暂定选择：

- 满员直接拒绝，不生成候补。好处是先集中练容量与并发；选候补则还要定义顺序、递补和取消后的重排。
- 所有学生都可报名，不以成员资格限制；所以普通退出社群不影响已有报名。
- 同一学生同一社群只允许一个“待审或有效”中的当前申请；待审可撤回，通过后可退出，之后再申请。
- 活动取消终止当前报名并保留经历；取消只处理原记录，不删除。当前负责人变更不改写历史活动的主办社群。
- 每个社群只有一位当前负责人，初建时可暂缺。历史负责人授权不在本次最小版中完整追踪；若需要，应另加授权期间，不拿当前负责人字段倒推出过去权限。

这些是答案选择，不是题目唯一允许的政策。若采用别的方案，先写出差异，再检查图、数据与查询是否一起变了。

## 4. 查询与四个例子

输入学号，返回当前社群名单，并能另看历次结束经历；输入活动，返回当前正式名单、人数及容量差；输入学生与活动，按时间返回每次受理及取消动作。

退出重入必须留下两次申请、两段经历；只在旧记录上清空退出时间会丢失第一段。最后一个名额最多一人成功，另一个满员拒绝；这只是要求，尚不是并发实现。重复点击返回已有当前报名，不新增一份；取消后的重新报名则是新的尝试。恰在截止点的报名与自助取消都拒绝。

“报过名”不等于“参加过”。本版本没有签到数据，因此不能声称能统计实际出席；要统计，就先增加相应需求。
